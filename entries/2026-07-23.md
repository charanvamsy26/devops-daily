# 2026-07-23 — Kubernetes DNS: CoreDNS and service discovery

**Area:** Kubernetes / Networking · **Tags:** `kubernetes` `coredns` `dns` `service-discovery`

## How names resolve inside a cluster

Every Service gets a DNS name of the form:

```
<service>.<namespace>.svc.cluster.local
```

Pods resolve through **CoreDNS** (a Deployment in `kube-system`, exposed by the `kube-dns` Service).
The kubelet writes each pod's `/etc/resolv.conf` to point at the cluster DNS IP, with search domains
so short names work:

```
nameserver 10.96.0.10
search demo.svc.cluster.local svc.cluster.local cluster.local
options ndots:5
```

That search list is why `curl http://api` works from the same namespace, and
`curl http://api.payments` reaches the `payments` namespace.

## Record types worth knowing

- **ClusterIP Service** → A record pointing at the virtual IP.
- **Headless Service** (`clusterIP: None`) → A records for **each pod IP** — this is how
  StatefulSets give stable per-pod identities (`pod-0.mysvc.ns.svc.cluster.local`).
- **SRV records** exist for named ports: `_https._tcp.mysvc.ns.svc.cluster.local`.

## The ndots:5 gotcha

With `ndots:5`, any name with fewer than 5 dots is tried against every search domain **first**.
An external lookup like `api.stripe.com` triggers several failed cluster-internal queries before the
real one — adding latency and CoreDNS load. Mitigations: use FQDNs with a trailing dot
(`api.stripe.com.`), tune `dnsConfig.options.ndots` per pod, or enable CoreDNS caching/autopath.

## Debugging DNS quickly

```bash
kubectl run -it --rm dnsutils --image=registry.k8s.io/e2e-test-images/agnhost:2.39 -- \
  nslookup kubernetes.default.svc.cluster.local
kubectl -n kube-system logs deploy/coredns | tail    # look for SERVFAIL/NXDOMAIN spikes
```

## Takeaway

Cluster DNS is just CoreDNS + a kubelet-managed resolv.conf: Services get predictable names,
headless Services expose per-pod records, and `ndots:5` is the classic hidden source of external
lookup latency.
