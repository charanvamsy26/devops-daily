# 2026-07-01 — GitHub Actions → AWS with OIDC (no long-lived keys)

**Area:** CI/CD / DevSecOps · **Tags:** `github-actions` `aws` `oidc` `iam` `secrets`

## The problem with static keys

The old way to let a CI pipeline touch AWS was to store an `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY`
as repo secrets. Those are **long-lived** — if they leak, they work until someone rotates them, and
rotation is manual and easy to forget. Better: no static credentials at all.

## OIDC: short-lived credentials via federation

GitHub Actions can act as an **OIDC identity provider**. AWS trusts it, and each job exchanges a
signed GitHub token for **temporary** STS credentials scoped to an IAM role — nothing stored.

**1) Register GitHub as an OIDC provider in AWS** (once per account):
`token.actions.githubusercontent.com`, audience `sts.amazonaws.com`.

**2) IAM role trust policy** — scope it to *your* repo so other repos can't assume it:

```json
{
  "Effect": "Allow",
  "Principal": { "Federated": "arn:aws:iam::<acct>:oidc-provider/token.actions.githubusercontent.com" },
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {
    "StringEquals": { "token.actions.githubusercontent.com:aud": "sts.amazonaws.com" },
    "StringLike":   { "token.actions.githubusercontent.com:sub": "repo:charanvamsy26/my-repo:ref:refs/heads/main" }
  }
}
```

**3) Workflow** — request the token and assume the role:

```yaml
permissions:
  id-token: write        # REQUIRED: lets the job mint the OIDC token
  contents: read
steps:
  - uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: arn:aws:iam::<acct>:role/github-actions-deploy
      aws-region: us-east-1
```

## Gotchas

- Forgetting `permissions: id-token: write` is the #1 failure — the token can't be minted.
- Lock the trust policy's `sub` to specific branches/environments; a loose `repo:org/*` is a
  privilege-escalation risk.
- Give the role least-privilege permissions, not `AdministratorAccess`.

## Takeaway

OIDC federation removes long-lived AWS keys from CI entirely: each run gets short-lived, tightly
scoped STS credentials. Pin the trust policy to your repo + branch and always set `id-token: write`.
