# 2026-06-28 — Multi-window, multi-burn-rate (MWMB) SLO alerting

**Area:** SRE / Observability · **Tags:** `slo` `prometheus` `alerting` `error-budget`

## The problem

A naive SLO alert ("page if the 5-minute error rate exceeds the budget") forces a bad trade-off:

- A **short** window reacts fast but is **noisy** — a 30-second blip pages someone.
- A **long** window is **quiet** but **slow** — you burn most of the month's budget before it fires.

You can't fix this with a single window.

## The idea: burn rate + two windows per alert

The **burn rate** is how fast you're spending the error budget relative to a sustainable pace:

```
allowed_error_ratio = 1 - SLO/100        # 99.9% -> 0.001
burn_rate           = observed_error_ratio / allowed_error_ratio
```

A burn rate of `1` exhausts the budget exactly at the end of the window; `14.4` would exhaust a
30-day budget in ~50 hours. Each alert tier fires only when **both** a long and a short window
exceed the threshold — the long window proves the burn is *sustained*, the short window proves it's
*still happening* (so the alert resolves quickly after an incident ends).

## The canonical 30-day table (Google SRE Workbook)

| Severity | Long / Short | Burn rate | Budget consumed |
| --- | --- | --- | --- |
| page   | 1h / 5m  | 14.4× | ~2% in 1h |
| page   | 6h / 30m | 6×    | ~5% in 6h |
| ticket | 1d / 2h  | 3×    | ~10% in 1d |
| ticket | 3d / 6h  | 1×    | ~10% in 3d |

The alert threshold for a tier is `burn_rate × allowed_error_ratio` — e.g. for a 99.9% SLO the
fast-burn page fires at `14.4 × 0.001 = 0.0144` (1.44% errors) sustained over 1h **and** 5m.

## Takeaway

Alert on **symptoms (budget burn), not causes**, and use paired windows to get fast detection
without flapping. This is exactly the logic I generate automatically in
[slo-operator](https://github.com/charanvamsy26/slo-operator).
