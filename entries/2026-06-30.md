# 2026-06-30 — Terraform remote state locking with S3 + DynamoDB

**Area:** Terraform / IaC · **Tags:** `terraform` `aws` `state` `locking` `s3` `dynamodb`

## Why state locking matters

Terraform's state file is the source of truth mapping config → real resources. If two people (or two
CI runs) `terraform apply` at the same time against shared state, they can **corrupt the state** or
race on the same resources. A **state lock** serializes writes so only one apply runs at a time.

## The classic S3 + DynamoDB backend

S3 stores the state; DynamoDB provides the distributed lock.

```hcl
terraform {
  backend "s3" {
    bucket         = "charan-tfstate-prod"
    key            = "eks/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "terraform-locks"   # holds the lock item
    encrypt        = true                 # SSE for state at rest
  }
}
```

The DynamoDB table only needs a primary key named **`LockID`** (String). When an apply starts,
Terraform writes a lock item; on completion it deletes it.

> Note: recent Terraform (v1.10+) added **S3-native locking** via `use_lockfile = true`, which can
> replace DynamoDB. DynamoDB remains the most widely deployed pattern in existing estates.

## Operational gotchas

- A crashed/killed apply can leave a **stale lock**. Inspect with the error's Lock ID, then
  `terraform force-unlock <LOCK_ID>` — only after confirming no apply is actually running.
- Enable **S3 versioning** on the state bucket so you can recover a previous state if it's corrupted.
- Lock down the bucket: block public access, least-privilege IAM, and a separate state bucket per
  environment/account.

## Takeaway

Shared Terraform state without locking is a corruption waiting to happen. S3 (storage + versioning +
encryption) plus DynamoDB (the `LockID` lock) is the battle-tested pattern; `force-unlock` clears a
stale lock when an apply dies.
