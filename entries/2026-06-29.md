# 2026-06-29 — Kubernetes requests vs limits: CPU throttling & OOMKills

**Area:** Kubernetes / Reliability · **Tags:** `kubernetes` `scheduling` `resources` `oomkill` `cgroups`

## Requests vs limits — two different jobs

- **`requests`** are used by the **scheduler** to decide which node a Pod fits on, and to compute a
  Pod's **QoS class**. They are a *reservation*.
- **`limits`** are enforced at **runtime** by the kernel (cgroups). They are a *ceiling*.

```yaml
resources:
  requests: { cpu: "100m", memory: "128Mi" }
  limits:   { cpu: "500m", memory: "256Mi" }
```

## CPU and memory are throttled very differently

- **CPU is compressible.** Exceeding the CPU *limit* doesn't kill the container — the kernel
  **throttles** it (CFS quota), so the app just runs slower and you see latency spikes. Watch
  `container_cpu_cfs_throttled_periods_total`.
- **Memory is incompressible.** Exceeding the memory *limit* gets the container **OOMKilled**
  (exit code 137) and restarted. There is no "slow down" for memory.

## QoS class decides who dies first under node pressure

| QoS | Condition | Eviction order |
| --- | --- | --- |
| Guaranteed | requests == limits for every container | last |
| Burstable | requests set, < limits | middle |
| BestEffort | no requests/limits | first |

## Practical rules of thumb

- **Always set memory `requests` == memory `limits`** for important workloads → Guaranteed QoS,
  predictable OOM behavior.
- **Set CPU `requests`, but be cautious with low CPU `limits`** — aggressive limits cause throttling
  that looks like a mysterious latency problem. Many teams set CPU requests and omit CPU limits.
- Size from real usage (e.g. `kubectl top`, Prometheus `container_memory_working_set_bytes`), not guesses.

## Takeaway

Requests are for *scheduling*, limits are for *runtime enforcement* — and hitting a CPU limit
throttles while hitting a memory limit kills. Get these wrong and you get phantom latency or
restart loops.
